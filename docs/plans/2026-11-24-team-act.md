# 任何机器都能管团队：team/act 与管理者（重写 R4）

- 日期：2026-11-24
- 相关：重写方案 `ds-bot-cluster/REWRITE-PLAN-2026-11-24.md` §2.6（用户选方案 A）；前置 R1–R3；配套 AC `rewrite/r4`

## 为什么

用户要求节点上的 Bot 能建任务、能管团队（"每台机器也能管"），但平常在主控上操作。原规则（2026-11-23）是节点上没有 Main Bot、节点 Bot 一律不能建 Bot / 改别的 Bot / 建群。用户 2026-11-24 选了方案 A：节点 Bot 有管理工具，但真正执行交给主控校验，主控仍是团队唯一的写者。

取舍：不为节点另写一套管理逻辑或权限规则，而是把调用**原样转给主控、以这个 Bot 在主控上的影子身份执行同一个工具**。节点 Bot 的能力因此和主控上处在同样位置的 Bot 完全一致，任何权限检查只有一份。也不把节点 Bot 的影子设成 Main Bot（那会影响侧栏、开场白和所有按 Main 判断的地方），而是新增一个只在管理工具里起作用的身份：管理者。

## 已定的行为

- **转发的工具**：`create_bot`、`update_bot`（改别的 Bot）、`delete_bot`、`stop_bot`、`create_group`、`update_group`、`delete_group`。在节点上调用时不在本地执行，发一个 `team/act` 帧给主控（`{ requestId, actor, tool, args }`，args 为 JSON，≤ 32 KiB），主控执行后回 `team/act-result`（`{ requestId, ok, text }`），工具结果就是主控那边的返回文本。主控 120 秒不答或链路不通，如实返回"没办成"。
- **本地照旧的**：Bot 改自己（`update_bot` 不带 bot 或带自己的名字），`task_start` 等后台任务，`message_bot`（R2/R3）。
- **在节点上建 Bot**：`create_bot` 不写 `node` 时，默认建在发起者所在的那台机器上。
- **管理者**：主控上，这 7 个工具的门槛从"Main Bot"放宽为"Main Bot 或管理者"。谁是管理者由主控的 `state.prefs.nodeManagers` 决定：`'all'`（默认，所有节点 Bot）、`'none'`，或 Bot 名字 / 影子 id 的列表。管理者能看见并管理所有群聊。
- **管理者的边界**：不能改、停、删 Main Bot（删 Main Bot 原本就不行）；`move_bot`、`promote_node_to_hub`、`team_health` 仍只给 Main Bot。
- **身份核对**：AC 主控只接受 actor 所在节点与发帧连接一致的请求；ds-bot 主控再按全队 id（R1/R2 的寻址）找到影子，影子必须属于那个节点。执行期间给这次调用临时登记一个会话归属（`team-act:<requestId>`），调用结束即删。

## AC：集群工具 ACL 接通

主控注册集群工具时把每机能力 ACL（read / write / delegate / shell / desktop）传进去了（原来写了没接）。只有主控状态目录里存在 `acl.json` 时才拦截，并热读；没有这个文件时不拦——ACL 默认禁止 shell/desktop，没配过 ACL 的团队不能因为升级突然失去远程执行。

## 不做什么（后续）

- 管理者名单的界面开关（现在只能改 state.json 的 `prefs.nodeManagers`）。
- 每台机器单独的 token 与"移出团队"即时吊销（AC 现在所有节点共用一个 token）：牵涉配对和主控鉴权，单独做。
- ACL 的面板编辑：R5 面板重做时一起。
